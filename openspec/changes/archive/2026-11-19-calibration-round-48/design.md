## Decisions

The lead made D1 to D8 on 2026-11-19 before this change was written. D9 to D12 are choices made while preparing it; each is marked as such.

D1. No simulator change. The fingerprint stays d45a275dd7be0713cec6a64394b7d8a9. The tools are the only code that changes. `calibrate --seeds` hands every child the same `--select-od` path, so seeds overwrite each other's file. The driver solves this by running one `calibrate --seed N --select-od FILE` process per seed. A change to the binary (a per-seed suffix on the path in `multi.rs`) would be about as large. The driver is the smaller risk: the report binary stays as every earlier round used it, and a child of `--seeds` is itself a single-seed run with the same arguments, so the output is the same. The driver gives up the multi-seed summary, which this loop does not use. The cost is the driver's own process handling (a pool of at most `--jobs` children, a log file per seed).

D2. Stations are chosen by rule behind a config switch that is off by default. The switch is the entry `countFit.throughTargets.simulatedMembership`. With it absent the committed build is byte-identical. It cannot be a committed `enabled: false` entry, because the demand's provenance records the config's hash and any text in the config changes both demand hashes; round 46 inserted its entry the same way, with a script on the laptop (`apply-candidate.py`). The rule: every fitted station with a target in the period for which `calibrate --select-od` writes pairs. That is link stations with a detector list (all ramp and turning-movement leg stations in the committed stations file) or counted at the block (volunteer-count blocks, Caltrans stations), and movement and route stations by their feature (`tools/lib/membership-loop.ts` `exportOf` mirrors `crates/sim/src/bin/calibrate.rs`). A ramp or turning-movement leg without a detector list stays static (none in the committed file). Gate totals stay static: they have neither links nor a route feature. Stations that exist only in the training build stay static too: the stations file is written by the shipped build, and the report binary exports only what it lists. These are the ramp stand-ins that carry an ADT x K target in place of a withheld counted leg: the on-ramps at nodes 725, 833 and 679 and the off-ramp at node 683. A training build with a made-up membership file left exactly these four static in PM and in AM (256 of 260 and 201 of 205 fitted stations); the fit report's "N of M fitted stations" shows the remainder. Periods other than the ones the loop runs stay static (midday, D4).

D3. No leak. The training view's proportions come only from runs of the training-view demand. The training membership file contains no station that the frozen split withholds, and none of the pairs only those stations used. Station choice and the stop rule never read a held-out score, an assessment or a count value. The frozen split is not touched. Implementation:

- Each seed run's manifest names the view of the demand it ran on (`demandBuild.view`). `checkRunSet` refuses a run of the other view, a duplicate seed, a run with other settings, and a set whose simulator, config, stations, split or targets hashes differ.
- The training file is filtered by `withheldStationIds(split)` (held stations plus the aggregates that overlap held blocks). `assertNoWithheld` checks the finished file, in the pair lists and in the zero-hit list, and stops before it is written. The file's pair totals keep only pairs that a kept station used.
- Station choice is `selectStations(stations file, split)`. A test renames every station and rescales every target and gets the same count.
- The loop reads no assessment output. Its stop rule reads simulated flows only.
- The driver hashes the split file before and after and stops if it changed. It never calls `data:split`.
- The shipped view fits every count, including the ones the split holds out, as the shipped build always has. Its membership file comes from shipped-demand runs and is only ever read by the shipped build (the training build refuses it through the view in the evidence).

One dependency stays, as in round 46 D7: turning movements that restate a held-out leg stay fitted in the training view, as the split's `retained` note says.

D4. Three iterations, fixed in advance. Pass 0 builds both views with static membership (the baseline's flows under this config) and runs seeds 1 to 10 for PM and AM. Pass k builds with the pool of passes 0 to k-1, runs the same seeds and pools passes 0 to k. The final build uses the pool of the last pass. Three passes of runs give three membership updates and a final build with the third. Runs are pooled with equal weight, so each pass weighs 1/n: the method of successive averages with step 1/n [PowellSheffi1982]. The entry in `docs/references.md` records that the paper's abstract (not the paper) says a predetermined step-size sequence converges for equilibrium assignment, and names 1/n as the standard choice. Using it on this fixed point (demand, routes, membership, demand) is an ASSUMPTION; no convergence is claimed. Early stop: after pass 1 or 2, if for every view and period the flow of each station and the flow of each pair at it moved less than the seed standard error (D11), the final build uses the pool so far and the remaining pass is skipped. Both PM and AM are built, because the demand file holds all periods and AM has its own held-out score (14 of 19). Midday is not run: it keeps static membership, its flows are fitted as before, and the keep rule does not score it. A midday run set can be added with `--periods pm_peak,am_peak,midday`, which adds half again to the seed runs.

D5. `priorTrips` stays 5 (ASSUMPTION, as in rounds 41 and 42). A sensitivity with 20 is optional (`candidates/simulated-membership-prior20.json`, its own file names and loop directory). Both values are assumptions; no value is sourced. It needs a second full loop, because the config hash is in the evidence.

D6. The driver fails loudly. After every build it reads the fit report. Pass 0 must say it had no membership file. From pass 1 the report must carry `Simulated membership from <file> (<view> view)` and, for each period of the file, the note with the number of pooled runs and of stations that took simulated membership, which must equal the number of stations the file holds. A report that says "lacks matching ... evidence. Using static membership." stops the loop. This is the known trap: the build falls back to static membership with a one-line note and the demand looks fine. The driver lists, every pass, the selected stations with zero simulated hits (D10) and the selected stations the runs did not export.

D7. Keep rule, round 46's D4 unchanged, written before any run. A candidate is adopted only if none of these is worse than the baseline:

- recent PM fitted stations within GEH 5: at least 74 of 92
- PM held out: at least 14 of 24
- AM fitted: at least 70 of 77
- AM held out: at least 14 of 19
- the baseline-calibration decision D5 holds, with 4 of 4 headline shares within 10 points
- all 8 whole-street traversal counts within GEH 5
- the baseline-calibration decision D16 (stability) holds in every period
- the validation suite still passes 67 of 74 at the same fingerprint

The station sets and denominators (92, 24, 77, 19) do not change. The rule is not loosened after a result. A figure one below its line fails the candidate. The screen is round 46's D6: three seeds (1 to 3), AM and PM, no verdict; the candidate gets the ten-seed assessment only if each of the four counts is no more than 3 stations below the baseline's own three-seed screen and no car is cleared from gridlock in the judged zone. The tolerance of 3 is an assumption about seed noise, written before any screen ran.

Reported, not conditions: the five diagonal stations in the PM (counted Forest St EB 66, McAuley St EB 12, 60th St EB 23, Ayala Ave NB 60, Howell St SB 17; sum 178) in the shipped and cross-validation view; Colby St NB; gate totals and the SR-24 mainline gate; mean through cars per hour in the study area; every SR-24 ramp, simulated against its count or target.

Round 42 raised the fitted score and lowered the held-out score, with sixteen hand-picked blocks. A candidate that raises PM fitted above 74 and leaves PM held out at 14 passes this rule, and a candidate that raises PM fitted by many and drops held out to 13 fails it. The held-out line is the one to read first. The fitted score will rise by construction here: the fit now plans with the simulator's own routes at the stations it is scored on. A rise in fitted stations alone is not evidence of a better model.

D8. Citations. Only keys already in `docs/references.md`, after reading the entry. [PowellSheffi1982] for the step rule, with the limits above. [VanZuylen1980] states the problem of estimating a trip table from link counts; only its title was read, and the entry says so. The method itself (fitting a trip table to counts with the assignment proportions taken from a simulator's runs, iterated) is labeled ASSUMPTION in the code, the config entry and the report. It needs literature that this change does not add. To find and verify before any claim of method: simulation-based or bi-level origin-destination estimation from link counts where assignment proportions come from a traffic simulator (for example SPSA-type and gradient approaches to dynamic OD estimation); the convergence of fixed-point iterations between a demand fit and a simulator's route choice; the choice of a prior weight for an observed share with few trips; and any published report on over-fitting of counted locations by such iteration (held-out count validation). No entry was added from memory.

D9. (Preparation choice.) The membership files are written under `target/membership/` (git-ignored) and not committed: with about 340 stations the pair lists reach megabytes, and the repository blocks files over 200 KB. The config entry names those paths. If a candidate is adopted, the files go to R2 with the other generated data.

D10. (Preparation choice.) A selected station with no simulated trip in any pooled run is left out of the file and keeps its static membership; it is listed in the file (`zeroHit`) and in every pass's report. If it were kept, its membership would be about zero and the fit could not reach its target at all. A station the runs did not export at all (a selected station missing from the binary's output) is listed too.

D11. (Preparation choice.) The stop rule. Per view and period, per station, the change in seed-mean flow between pass k and pass k-1 is compared with the combined standard error of the two means, as a ratio of root mean squares over stations. The same is done for the sum over pairs at a station of the change in seed-mean pair flow. Two samples of one distribution give a flow ratio near 1 and a pair ratio below 1, so the threshold is 1 for both (ASSUMPTION, written before any run). The loop stops only if both are at most 1 in every view and period.

D12. (Preparation choice.) Through-car targets (the four street runs of round 39) and the hand-picked `measuredStations` list stay as they are while the entry is present: the through targets are static, as in the baseline, and the list is replaced by the rule. This keeps the effect of the round to the station rule.

D13. The heavy runs (builds that need the simulator's fingerprint, seed runs, screens, validation, assessments) run on the user's laptop from `runbook.md`. This change was prepared in a cloud container: no simulation ran.

## What is not known

- Whether the loop runs end to end. The driver was tested against a fake build and a fake simulator that write the files the real ones write, and the `Simulated membership` path of the build was reached once with a made-up file, but `calibrate --select-od` was never run from the driver. In particular the single-seed `calibrate --seed N --demand COPY --select-od FILE --no-write` call, and that the manifest accepts a demand file copied out of `public/data`, are read from the code and not run.
- Whether the stations file stays byte-identical across builds (the evidence hashes it). It holds targets only, and the driver stops if its hash changes after the first shipped build.
- How long a build takes with about 340 stations on simulated membership. The made-up-file build gives one measurement (below), not one with real pairs.
- Whether the simulator's pairs make a station's target reachable. A station whose simulated pairs are few has a membership near its static share through the prior of 5 trips; a station none of whose pairs the simulator uses is left static (D10).
- Whether iterating moves the result. Round 44's feedback loop moved flows toward the diagonal because the fit followed the simulator's costs. Here the fit follows the simulator's membership at the counted stations, and no run says which way the through volume goes.

## Risks

- Fitted stations rise and held-out stations fall, as in round 42. The keep rule's held-out lines are the guard, and the screen shows it early on three seeds.
- Pair shares measured at ten seeds are noisy for pairs with few trips. Equal-weight pooling over passes helps, and the prior of 5 limits what one pair can do.
- A fit that matches counts through the simulator's routes can remove through trips that the simulator then needs to fill gates. The reported through cars per hour and the SR-24 gate totals show it.
- The loop's memory of the first pass is permanent in the pool (1/n weighting), so a first pass that is far from the later ones keeps pulling. The stop rule and the pass count are the only controls.
