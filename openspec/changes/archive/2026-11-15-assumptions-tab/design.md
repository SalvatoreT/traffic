## Context

Project lead feedback on the Sources page, 2026-11-15: the assumed movement flows section could be easier to read and should not say "owner"; the reasons cars cut through could each have a simple map; both could go in a separate Assumptions tab before Sources, or something implying they are more discretionary. A proposal search was running against the current demand file, so the demand file could not be rebuilt or edited.

## Decisions

- **Separate tab before Sources, named Assumptions.** Decision of the project lead. Other assumptions listed on Sources stay there; only these two sections move.
- **Data outside the hashed demand file.** The table's numbers come from the demand config (movements, intents, detour limit, count periods) joined to the fit report's two assumed-movement tables, written by `tools/build-assumptions.ts` to `<area>.assumptions.json`. The file records the demand hash; the tab says so when it differs from the loaded demand, and still shows the table. The fit report is markdown, so the parser fails loudly when a table changes shape. Alternative considered: carry the table in `areas.json`. Rejected because the manifest then depends on the demand build order and the file is regenerated by a tool that is fast either way.
- **Counted versus assumed.** The count measured AM and PM only; midday is the count scaled by the assumed period volume factors (`volunteerCount.middayFromPm`), so its column is marked scaled. Assigned, through and the intent shares are assumptions. A through intent is one whose origin and destination groups both lie outside the study area.
- **Shares in the table** are each intent's share of the cars assigned to that turn in the lead period, from the report's per-intent volumes, so they sum to 100% and can differ from the config's shares of the counted volume.
- **Baseline by reason precomputed.** `baseline-intents.json` holds, per period, cars an hour by intent and the Float32 (slot, link, vehicles) triples of the baseline run, at the app's seed and run length, with network hash, demand hash and simulator fingerprint. The app applies it under the same rule as stored results and otherwise shows the cards without maps and with a one-line note. No simulation runs on page load.
- **Map drawing.** The frame, streets and boundary names come from `buildBaseMap`, extracted from the proposal picture so the look matches. The path is the live highlight's dashed violet line with its casing; width is `pathWidth` at 0.6 of the live scale because the card is a few hundred pixels wide (ASSUMPTION, display scale). Each long link gets an arrowhead. "From" and "To" labels name the arterials the path leaves and rejoins, found by the same crossings the text description uses (`pathEnds`). Where both directions of a street are on the path and one carries under half of the other, only the heavier is drawn. The map is an `svg` with `role="img"` and an alt text that repeats the text description.
- **Hidden provenance.** The UI drops provenance entries whose source starts with "Assumed movement flows" from Sources. The builder now writes a short entry so the next rebuild carries clean text.
- **Wording.** No "owner" in user-facing text, config notes or data docs; the decision is stated, or the person is "the project lead".

## Risks

- The fit report parser depends on the report's table headings. A tool test covers the shape; a change makes `npm run data:assumptions` fail instead of writing wrong numbers.
- Maps need the simulator fingerprint, so they appear once the engine has started.
